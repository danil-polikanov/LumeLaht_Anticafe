# Анализ идеи дипломной работы: LumeLaht Anticafe

## Текущее состояние проекта

**Что уже есть:**
- **Frontend:** React 19 + TypeScript, FSD-архитектура (app/entities/features/pages/shared/widgets), Redux Toolkit, React Router, Bootstrap
- **Backend:** .NET 9, два проекта:
  - `LumeLaht_Anticafe` — основной проект (monolith?)
  - `LumeLaht_RoomApi` — отдельный API с Clean Architecture (Core → Application → Infrastructure → API)
- **Тесты:** `LumeLaht_RoomApi.Tests`
- **БД:** миграции и seed data (rooms, activities, addresses)

---

## Подходит ли идея для дипломной работы?

**Да, подходит отлично.** Вот почему:

1. **Практическая значимость** — реальный бизнес-кейс (антикафе LumeLaht для эстонского рынка)
2. **Научная новизна** — эмпирическое сравнение 3 архитектур на одном и том же стеке (.NET + React), а не теоретическое описание
3. **Измеримые результаты** — нагрузочное тестирование дает количественные данные для анализа
4. **Соответствие требованиям Narva Kolledž** — структура с теорией, методологией, результатами и выводами

Из презентации `loputoode_struktuur.pptx` требуются:
- Проблема и новизна (есть — мало эмпирических сравнений на современном стеке)
- Гипотеза или исследовательский вопрос (есть)
- Методология (нагрузочное тестирование)
- Результаты и их оценка (метрики производительности)
- Выводы и рекомендации

---

## 3 архитектуры для сравнения

| # | Архитектура | Описание | Что нужно реализовать |
|---|-------------|----------|----------------------|
| 1 | **Monolithic** | Всё в одном проекте: React SSR/SPA + C# API + БД | Один .NET проект с встроенным фронтендом (или SPA, обслуживаемый тем же сервером) |
| 2 | **Separated (Client-Server)** | React SPA отдельно + один .NET API отдельно | Это по сути то, что уже частично есть (frontend + LumeLaht_RoomApi) |
| 3 | **Microservices** | React SPA + несколько микросервисов (RoomService, BookingService, UserService и т.д.) + API Gateway | Разделить бэкенд на 2-3 независимых сервиса, Docker Compose |

---

## Что нужно добавить / доработать

### 1. Архитектурные реализации

- **Monolith:** Создать версию, где .NET проект обслуживает и API и фронтенд. Можно использовать Razor Pages + React embedded или просто .NET сервер, раздающий SPA + API в одном процессе
- **Separated:** Довести текущую версию до полнофункционального состояния (frontend отдельно, один API отдельно)
- **Microservices:** Разбить бэкенд на 2-3 сервиса:
  - `RoomService` — управление комнатами и активностями
  - `BookingService` — бронирования
  - `UserService` (опционально) — аутентификация
  - API Gateway (Ocelot или YARP)
  - Межсервисная коммуникация (HTTP или RabbitMQ)

### 2. Dockerизация (обязательно)

- `Dockerfile` для каждого сервиса/архитектуры
- `docker-compose.yml` для каждого варианта
- Это обеспечивает **одинаковые условия тестирования** и воспроизводимость

### 3. Нагрузочное тестирование (ключевая часть)

**Инструменты:**
- **k6** (от Grafana Labs) — основной инструмент для load testing, пишется на JS
- **Prometheus** — сбор метрик (response time, CPU, RAM, error rate)
- **Grafana** — визуализация результатов

**Сценарии тестирования:**
| Сценарий | Описание | Зачем |
|----------|----------|-------|
| Constant Load | Фиксированное число VU (virtual users), например 50, на 5 мин | Базовая производительность |
| Ramp-Up | Постепенное увеличение 10 → 200 VU | Как система масштабируется |
| Spike Test | Резкий скачок нагрузки (10 → 500 → 10 VU) | Устойчивость к пиковым нагрузкам |
| Soak Test | Длительная нагрузка (30-60 мин) | Утечки памяти, деградация |

**Метрики для сравнения:**
- Response time (p50, p95, p99)
- Throughput (requests/sec)
- Error rate
- CPU utilization
- Memory utilization
- Время холодного старта (cold start)

### 4. Функциональность приложения (минимум для всех 3 версий)

Все 3 архитектуры должны реализовывать **одинаковый** функционал:
- Просмотр списка комнат с фильтрацией
- Детальная страница комнаты
- Бронирование комнаты (создание/отмена)
- Базовая аутентификация (JWT)
- CRUD для бронирований

### 5. Статистический анализ результатов

Для дипломной работы недостаточно просто показать графики — нужен **статистический анализ**:
- Описательная статистика (mean, median, стандартное отклонение)
- Сравнительный анализ (можно использовать t-test или ANOVA для сравнения response times)
- Визуализация: box plots, гистограммы, line charts
- Минимум 3-5 прогонов каждого теста для статистической значимости

### 6. Дополнительные аспекты (для усиления работы)

- **Сравнение Developer Experience (DX):** сложность разработки, количество строк кода, время деплоя
- **Операционная сложность:** количество контейнеров, сложность CI/CD, мониторинг
- **Анализ стоимости:** примерные затраты на хостинг для каждой архитектуры (на основе потребления ресурсов)
- **Таблица trade-offs:** сводная таблица плюсов/минусов каждой архитектуры по всем метрикам

## План действий (приоритет)

### Фаза 1: Доработка функционала (основа)
1. Определить минимальный набор функций (rooms CRUD, booking, auth)
2. Довести Separated-версию до рабочего состояния (это база)
3. Добавить бронирование и аутентификацию

### Фаза 2: Создание архитектурных вариантов
4. Создать Monolith-версию (объединить фронт и бэк)
5. Создать Microservices-версию (разделить на сервисы + API Gateway)
6. Docker Compose для всех трёх вариантов

### Фаза 3: Тестирование и анализ
7. Настроить Prometheus + Grafana
8. Написать k6-скрипты для всех сценариев
9. Провести тестирование (минимум 3-5 прогонов на сценарий)
10. Собрать и проанализировать данные

### Фаза 4: Написание работы
11. Теоретическая глава (обзор литературы)
12. Методология
13. Результаты и обсуждение
14. Введение и заключение (пишутся последними)

## Риски и рекомендации

| Риск | Митигация |
|------|-----------|
| Слишком много работы — 3 полных реализации | Минимальный функционал, общий фронтенд для separated и microservices |
| Нестабильные результаты тестов | Несколько прогонов, Docker для изоляции, статистический анализ |
| Микросервисы слишком сложны | Ограничиться 2-3 сервисами, использовать Docker Compose (не Kubernetes) |
| Нет реальных пользователей для usability testing | Фокус на нагрузочном тестировании (количественные данные), usability — опционально |

## Вывод

Идея **отлично подходит** для бакалаврской работы. Она объединяет:
- Практическую разработку (3 архитектуры реального приложения)
- Научный подход (эмпирическое тестирование, статистический анализ)
- Актуальность (современный стек: .NET 9, React 19, Docker, k6)
- Измеримые результаты (числа, графики, статистика)

Главное — не перегружать себя функционалом приложения. Минимальный MVP (комнаты + бронирование + аутентификация) достаточен. Фокус работы — на **сравнении архитектур**, а не на фичах антикафе.
